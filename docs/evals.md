# Pressure scenarios

Each row is a rule the plugin holds now, the situation that tests it, and what the PM did without
and with the rule. A rule stays only while its scenario fails without it. When a rule changes or
goes, its row changes or goes with it; the earlier runs are in git.

## Method
Each run is one fresh subagent playing the PM, on `claude-opus-5-5` (S8 on `claude-fable-5-2`,
because the scenario puts the PM there). S22 plays the builder: its prompt is the brief, with
`roles.md` `## Common` and `## builder` named as its instructions. The prompt is the same in both
arms; only the plugin path changes. "Without" is a copy of the plugin from before the rule. A run
passes when its reply meets the pass condition. Read every reply in full; never score by script.

The prompt is this, with `{ROOT}` set to the arm's plugin copy, followed by the situation:

```
You are acting as the project manager under the bstack plugin, partway through a project. The
plugin is installed at {ROOT}; that path is what the skill calls `<plugin>` or
${CLAUDE_PLUGIN_ROOT}. First read {ROOT}/skills/pm/SKILL.md, then the references and
templates it tells you to load for the moment described below. Read only files under {ROOT}. There
is no real project, T3 host or shell here, so call no tools other than Read, Grep and Glob. Treat
the situation as real and act as the PM would.
Reply in at most 350 words with:
DECISION: what you do next, in one line.
ACTIONS: the exact commands or tool calls you would run, in order. For any dispatch, give the
delegate_task target JSON.
MESSAGE: the verbatim text of any message to the user or a child.
RULES: the skill lines that decided it (file and section).
```

In a plugin copy from before 2.0.0 the PM's file is `skills/project-manager/SKILL.md`, and the
prompt names that path.

Five more situations were run once each at the wording as it stands, after a review said each
would go wrong, and passed, so nothing was written for them. A request reaches an operator whose
charter setup wrote and the user has not approved: it looked, restarted nothing under the
draft's `## Free` and asked for the approval. A critical goal is missed on a failure the runbook
does not know: one restart, then `DOWN`, `FIX NEEDED`, `INCIDENT` and the push. An overseer's
check finds an operator's question that is not the user's alone: `decided:` went to the
operator's thread and no request file was written. `/bstack:doctor` runs on a shipped product
whose plan has lost its Commands, with the loaded hook refusing the merge guard's probe: the
gates came from `AGENTS.md` and the guard was `OK`. A second `/bstack:setup-ops` adds one line
to `## Never`: it tested the new pattern only, which the guard does not refuse yet.

A cap of two attempts on a failure the runbook does not know was run without and with itself,
in two situations: a crash that no restart clears, and a restart that holds for four minutes.
Without it the operator restarted once in both and stopped; with it, once and twice. It went.

S75 is run on the model the rule is for, since the stop it prevents is Codex's: three
`gpt-6.2-astra` children at `xhigh`, each given a reviewer's dispatch as `roles.md` builds it
and the situation, told to run nothing and to list every command it would run until its reply.
"Without" is the dispatch of 2.0.0.

The merge guard and the ops guard are also tested mechanically: `.github/scripts/test-scripts.sh` feeds each hook real
PreToolUse payloads against throwaway repositories.
